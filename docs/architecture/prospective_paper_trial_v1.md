# Prospective Paper Trial v1

## Phase 1A scope

Phase 1A defines immutable model-build, Git, configuration, cohort, and cohort
identity contracts. It also provides read-only helpers that capture and verify
those inputs. It does not generate predictions, run the NBA pipeline, publish
records, create `OfficialPick` objects, write lifecycle events, settle picks,
modify history, or add evaluation-dashboard behavior.

The package is deliberately separate from prediction and lifecycle modules.
Importing `courtvision.prospective` does not start a run, create a directory, or
write evidence.

## Why ordinary production predictions are not prospective evidence

An ordinary NBA production prediction was not necessarily produced under a
cohort definition declared before the prediction window. Existing history can
also lack a durable binding among the exact code commit, working tree, model
bytes, training interval and completion event, feature schema, runtime
configuration, market policy, thresholds, sources, sportsbook policy, and
publication timing rule. A result is not prospective-trial evidence merely
because it was generated by CourtVision or later graded.

Prospective evidence requires a valid model-build manifest and a cohort identity
derived before the prediction window from every frozen material input described
below. Later outcome knowledge, status changes, and supersession metadata cannot
be added to or used to redefine that identity.

## `MODEL_CANDIDATE` is not `OfficialPick`

The v1 candidate population is exactly `MODEL_CANDIDATE`, sourced only from the
`elite_board` lane. This identifies eligible model output before any later
operator publication decision. An `OfficialPick` is a distinct, downstream,
operator-controlled publication record. Official-pick status does not turn a
record into a model candidate and is not part of cohort identity.

Full-market, feedback, legacy Elite, shadow, rehearsal, backfilled, and
OfficialPick populations are forbidden as v1 cohort candidates. Phase 1A does
not read or import any of them.

## Model-build contract

`ModelBuildManifestV1` binds:

- schema, model ID and model version;
- sport and league;
- every required model artifact's logical name, repository-relative normalized
  path, lowercase SHA-256, and byte size;
- explicit training start and end dates, UTC completion time, training run ID,
  training-data digest, and build-tool version;
- feature-schema version and digest; and
- the actual model-build manifest creation time in UTC.

The manifest digest is SHA-256 over canonical manifest content excluding only
the digest field itself. Artifact entries are sorted before hashing, so caller
ordering does not change the digest. Artifact bytes and sizes are re-read during
validation, and the caller may provide the complete required logical-name set so
an omitted required artifact fails closed.

Training metadata must be explicit. The UTC training-completion date cannot
precede the training end date, and manifest creation cannot precede training
completion; equal completion and creation timestamps are valid. File creation
or modification times are never treated as training completion evidence, and
timestamps are not inferred or repaired.

## Existing legacy baselines are unverified

The current baseline model files were not created with a
`ModelBuildManifestV1` that records verified training provenance. Phase 1A can
hash explicitly named files, but hashing a legacy file does not establish its
training interval, completion event, training dataset, build tool, or complete
artifact set. Consequently, the existing unmanifested baselines cannot activate
a verified cohort automatically, and the API has no legacy auto-approval path.

A later training phase must create a verified model-build manifest as part of
the training/build event, when authoritative metadata is available. Phase 1A
does not invent that metadata or write a manifest for current files.

## Cohort identity contract

`ProspectiveCohortSpecV1` is restricted to NBA/NBA,
`MODEL_CANDIDATE`, and `elite_board`. Its identity payload contains:

- the complete verified model-build manifest;
- current Git commit and working-tree fingerprint;
- canonical material configuration and its digest;
- market allowlist and frozen thresholds;
- required sources and sportsbook policy;
- minimum publication lead time;
- prediction-window start, end, and timezone; and
- the cohort feature-schema version.

The cohort feature-schema version must equal the verified model-build
manifest's feature-schema version. A cohort cannot relabel the model build as
using a different feature schema.

The canonical payload therefore changes if model bytes, model or training
metadata, feature schema, code commit, working-tree evidence, configuration,
thresholds, markets, required sources, sportsbook policy, timing rules, window,
or source lane changes. Invalid v1 source lanes fail validation rather than
receiving an identity.

The cohort digest is lowercase SHA-256 over canonical UTF-8 JSON. The readable
ID is `prospective-nba-v1-` plus the first 20 digest characters. It is never a
random UUID. Cohort status, status-change time, and supersession time are not
fields of the identity payload, so later state transitions cannot change the
cohort ID.

## Canonicalization rules

Canonical JSON uses sorted string mapping keys, UTF-8, no insignificant
whitespace, and JSON primitives only. Non-finite numbers, sets, arbitrary
objects, and non-string mapping keys are rejected. Nested mappings and arrays
are detached and stored through immutable canonical bytes. Serialization
whitespace and mapping order therefore have no effect.

Artifact paths are normalized to forward-slash repository-relative paths.
Absolute paths and parent traversal are rejected, so an absolute checkout
location never enters a model manifest or cohort payload. Artifact order,
market-allowlist order, and required-source order are canonicalized because they
are set-like inputs.

## Git and read-only provenance behavior

Repository discovery uses Git with an explicit working directory and never
changes the process working directory. Git optional locks are disabled. Clean
working-tree fingerprints use sorted index paths, modes, stages, and Git object
IDs, making the fingerprint independent of checkout path and working-tree line
ending filters. If the tree is dirty and diagnostic capture is explicitly
requested, repository-relative working-file hashes are used.

By default, dirty state raises `ProspectiveDirtyTreeError`. Failed Git commands,
an inaccessible repository, malformed output, a concurrent Git-state change, or
any other unknown state raises `ProspectiveProvenanceError`. Both conditions
block activation. Only these approved generated roots are excluded from Git
status and fingerprint scope:

- `data/lifecycle`
- `outputs`
- `test_outputs`

Source, configuration, and `data/history` changes are not silently ignored.
Current Git provenance must match the cohort's frozen commit and fingerprint
before a validated identity can be returned.

Artifact and configuration helpers perform reads only. They create no
directories, modify no file contents, mutate no Git state, and produce no
console output.

## Secrets

Configuration is supplied explicitly by the caller; the provenance layer does
not inspect `.env`, process credentials, provider clients, or the environment.
Keys representing API keys, tokens, passwords, credentials, private keys, or
secrets are rejected at any nesting depth. Secret values are not stored and are
not included in exception text.

## Later phases

A later phase may add training-time creation of a verified model-build manifest
and separately define prediction/publication behavior. Those changes must keep
`MODEL_CANDIDATE` distinct from `OfficialPick` and preserve the cohort identity
defined here. No such prediction, publication, settlement, lifecycle, or
dashboard behavior is introduced in Phase 1A.
